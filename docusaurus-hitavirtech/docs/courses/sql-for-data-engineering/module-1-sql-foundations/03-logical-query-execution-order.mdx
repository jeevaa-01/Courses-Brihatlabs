> *"Make it work, make it right, make it fast — in that order."*
> — Kent Beck

:::info[HitaVir Tech connection]
"Make it right" starts with knowing how the engine actually reads your query. SQL is *declarative* — you describe the result you want, and the database decides the path. The clauses do **not** run in the order you write them.
:::

:::tip[Why this matters now]
Almost every "why doesn't this work?" SQL error — an alias that won't resolve, a `WHERE` that rejects an aggregate, a `HAVING` you didn't need — comes straight from this one diagram. Learn it once and those errors stop being mysterious.
:::

You write a query top-to-bottom starting with `SELECT`, but the database runs the clauses in a completely different order. `SELECT` — the first thing you type — is actually the **fifth** thing that runs. This single fact explains a huge share of beginner SQL bugs.

![Logical execution order of a SQL query](/img/courses/diagrams/sql/logical-execution-order.svg)

### Written order vs run order

| You **write** (top → bottom) | SQL **runs** (logical order) |
|------------------------------|------------------------------|
| `SELECT`                     | 1. `FROM` / `JOIN`           |
| `FROM` / `JOIN`              | 2. `WHERE`                   |
| `WHERE`                      | 3. `GROUP BY`                |
| `GROUP BY`                   | 4. `HAVING`                  |
| `HAVING`                     | 5. `SELECT`                  |
| `ORDER BY`                   | 6. `DISTINCT`                |
| `LIMIT`                      | 7. `ORDER BY`                |
|                              | 8. `LIMIT`                   |

### Trace a real query through the phases

Take the professional query from the previous page and follow it down the pipeline:

```sql
SELECT
    c.customer_id,
    c.full_name,
    SUM(oi.line_amount) AS total_revenue
FROM customers   AS c
JOIN orders      AS o  ON o.customer_id = c.customer_id
JOIN order_items AS oi ON oi.order_id   = o.order_id
WHERE o.order_date >= '2026-01-01'
  AND o.order_date <  '2027-01-01'
GROUP BY c.customer_id, c.full_name
ORDER BY total_revenue DESC
LIMIT 5;
```

1. **`FROM` / `JOIN`** — build one big set of rows: every order item joined to its order and customer.
2. **`WHERE`** — drop every row whose `order_date` is outside 2026. (No aggregates exist yet, so you cannot filter on `SUM` here.)
3. **`GROUP BY`** — fold the surviving rows into one group per `(customer_id, full_name)`.
4. **`HAVING`** — filter whole groups (none filtered here).
5. **`SELECT`** — now compute `SUM(oi.line_amount)` and name it `total_revenue`. **The alias is created at this step — not before.**
6. **`DISTINCT`** — remove duplicate result rows (none here).
7. **`ORDER BY total_revenue DESC`** — sort. This works because `SELECT` already ran, so the `total_revenue` alias exists.
8. **`LIMIT 5`** — keep only the first five sorted rows.

### Three bugs this one diagram explains

- **`WHERE total_revenue > 1000` fails.** `total_revenue` is a `SELECT` alias (step 5), but `WHERE` runs at step 2 — the alias does not exist yet. Filter aggregates in `HAVING`, or repeat the full expression.
- **`WHERE` vs `HAVING`.** `WHERE` filters individual **rows before** grouping; `HAVING` filters whole **groups after** aggregation. `WHERE SUM(...) > 100` is illegal; `HAVING SUM(...) > 100` is correct.
- **`ORDER BY total_revenue` works.** `ORDER BY` runs at step 7, *after* `SELECT` (step 5), so `SELECT` aliases are visible there — which is why sorting by an alias is allowed but filtering by one is not.

:::info[Pro Insight]
Senior engineers debug SQL by mentally walking this pipeline. When a query misbehaves, they ask "which phase am I in?" — and the answer almost always points straight at the fix.
:::

<KeyTakeaways>

- SQL runs `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT` — not the order you write
- `SELECT` aliases are created at phase 5, so `ORDER BY` (phase 7) can use them but `WHERE` (phase 2) cannot
- `WHERE` filters individual rows before grouping; `HAVING` filters whole groups after aggregation
- When a query misbehaves, ask "which phase am I in?" — the answer points at the fix

</KeyTakeaways>
