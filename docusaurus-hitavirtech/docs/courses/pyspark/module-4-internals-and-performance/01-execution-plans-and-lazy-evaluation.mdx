# Execution Plans and Lazy Evaluation

*⏱ Estimated time: 70 minutes*

:::note[🎯 Learning objectives]

By the end of this section, you will be able to:

- Read `explain()` output and identify Scan, Filter, Exchange, and Aggregate nodes.
- Distinguish narrow from wide transformations and explain what a shuffle costs.
- Describe predicate pushdown and column pruning.

:::

### Explain a plan

```python
result_df.explain()
```

Detailed:

```python
result_df.explain("formatted")
```

### Plan stages

Spark builds:

1. Parsed logical plan.
2. Analyzed logical plan.
3. Optimized logical plan.
4. Physical plan.

### Narrow transformations

Examples:

- `select`
- `filter`
- `withColumn`
- `mapPartitions`

These usually operate within existing partitions.

### Wide transformations

Examples:

- `groupBy`
- `join`
- `distinct`
- `repartition`
- `orderBy`

These often cause shuffles.

### Shuffle

A shuffle moves data between partitions or executors.

Shuffles can be expensive because of:

- Network transfer.
- Disk I/O.
- Serialization.
- Sorting.
- Memory pressure.

### Predicate pushdown

When reading Parquet:

```python
filtered_df = (
    spark.read
    .parquet(f"{BASE_PATH}/processed/sales_by_region")
    .filter(F.col("region") == "SOUTH")
)
```

Spark may read only relevant partitions and row groups.

### Column pruning

```python
selected_df = spark.read.parquet(
    f"{BASE_PATH}/processed/clean_sales"
).select(
    "transaction_id",
    "region",
    "revenue"
)
```

Spark reads only needed columns where supported.

### ✅ Checkpoint

regional_summary_df.explain("formatted")

:::info[📌 Key takeaways]

- Lazy evaluation lets Catalyst optimize the whole plan before running anything.
- Wide transformations cause shuffles; narrow ones stay within partitions.
- Most major performance problems are visible in the physical plan.

:::
